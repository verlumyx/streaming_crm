# Next.js Module — Commands

Commands are typed Data Transfer Objects (DTOs) that carry data between layers (action/page → Service → Repository). They contain **no business logic**.

## Location

```
src/modules/{module-name}/commands/
├── create-{module-name}.command.ts          Create{Module}Command
├── update-{module-name}.command.ts          Update{Module}Command
├── update-status-{module-name}.command.ts   UpdateStatus{Module}Command
└── search-{module-name}.command.ts          Search{Module}Command
```

## Rules

1. All fields **must** be `readonly`.
2. No methods except the `fromInput()` static factory.
3. No business logic — only data transportation. No defaults that encode a rule, no formatting, no lookups.
4. `fromInput()` maps the **validated** input (`{X}Input`, the `z.infer` type of the matching schema in `validation/`) to the command. Never build a command from raw `FormData`.
5. `companyId` always comes from the `[companyId]` URL segment, never from the form or the session. It is the second argument of `fromInput()` on Create and a required field on Search.
6. One command per action: Create, Update, UpdateStatus, Search. A new use case gets its own command.
7. `Search{Module}Command` always includes `filters`, `limit`, `offset` and `companyId`; the keys of `filters` **must** match the keys of the repository filter map (`repositories/{module-name}.filters.ts`).

## Create{Module}Command

The `id` field is **always the first field** in Create commands. It carries the UUID v7 generated by the client and validated by the create schema. `companyId` is always the second.

```ts
// src/modules/client/commands/create-client.command.ts
import type { CreateClientInput } from '../validation/create-client.schema';

export class CreateClientCommand {
  constructor(
    readonly id: string,
    readonly companyId: string,
    readonly name: string,
    // add fields as needed
  ) {}

  static fromInput(input: CreateClientInput, companyId: string): CreateClientCommand {
    return new CreateClientCommand(input.id, companyId, input.name);
  }
}
```

## Update{Module}Command

No `id` and no `companyId`: both are passed to the Service as separate arguments (`updateService.execute(id, companyId, command)`), so the command only carries the editable fields.

```ts
// src/modules/client/commands/update-client.command.ts
import type { UpdateClientInput } from '../validation/update-client.schema';

export class UpdateClientCommand {
  constructor(
    readonly name: string,
    // add fields as needed
  ) {}

  static fromInput(input: UpdateClientInput): UpdateClientCommand {
    return new UpdateClientCommand(input.name);
  }
}
```

---

## UpdateStatus{Module}Command

Carries **only** `status`. As with Update, `id` and `companyId` travel as separate Service arguments.

```ts
// src/modules/client/commands/update-status-client.command.ts
import type { UpdateStatusClientInput } from '../validation/update-status-client.schema';

export class UpdateStatusClientCommand {
  constructor(readonly status: 'active' | 'inactive') {}

  static fromInput(input: UpdateStatusClientInput): UpdateStatusClientCommand {
    return new UpdateStatusClientCommand(input.status);
  }
}
```

## Search{Module}Command

Filters are passed as a single `filters` object (criteria pattern). This allows the Repository to iterate over them with `applyFilters()` without the Command needing to know the available filter keys.

`companyId` is a **dedicated, required field** (not a filter key). Company scoping must travel through the Command so the Repository never reads cookies, headers or the session. The page fills it from the `[companyId]` URL segment.

```ts
// src/modules/client/commands/search-client.command.ts
export class SearchClientCommand {
  readonly filters: Record<string, string | undefined>;
  readonly limit: number;
  readonly offset: number;
  readonly companyId: string;

  constructor(params: {
    filters?: Record<string, string | undefined>;
    limit?: number;
    offset?: number;
    companyId: string;
  }) {
    this.filters = params.filters ?? {};
    this.limit = params.limit ?? 20;
    this.offset = params.offset ?? 0;
    this.companyId = params.companyId;
  }
}
```

`undefined` and `''` values inside `filters` are skipped by `applyFilters()`, so the page can pass every parsed search param as-is.

## Instantiation

Commands are always created in the server action (mutations) or in the page (search) — never inside a Service or Repository — right after the input has been validated with the module's Zod schema.

### In `actions.ts` (mutation use cases)

```ts
// src/app/[companyId]/clients/actions.ts
const parsed = createClientSchema.safeParse(Object.fromEntries(formData));
if (!parsed.success) return { status: 'error', fieldErrors: parsed.error.flatten().fieldErrors };

// Crear — id comes from the form, companyId from the URL segment
await createClientContainer(tx).createService.execute(
  CreateClientCommand.fromInput(parsed.data, companyId),
);

// Actualizar — id and companyId are bound arguments of the action
await createClientContainer(tx).updateService.execute(
  id,
  companyId,
  UpdateClientCommand.fromInput(parsed.data),
);

// Actualizar Estado
await createClientContainer(db).updateStatusService.execute(
  id,
  companyId,
  UpdateStatusClientCommand.fromInput(parsed.data),
);
```

### In `page.tsx` (search use case — criteria pattern)

```tsx
// src/app/[companyId]/clients/page.tsx
const { companyId } = await params;
await guardPage(companyId, 'clients.list');

const filters = searchClientSchema.parse(await searchParams);

const command = new SearchClientCommand({
  filters: { search: filters.search, status: filters.status }, // keys == clientFilters keys
  limit: filters.limit,
  offset: filters.offset,
  companyId,
});

const { data, total } = await createClientContainer(db).searchService.execute(command);
```

Adding a filter means touching three places in lockstep: the search schema (`validation/search-{module-name}.schema.ts`), the `filters` object built in the page, and the filter map in `repositories/{module-name}.filters.ts`. See `nextjs-module-repositories` for the last one.
