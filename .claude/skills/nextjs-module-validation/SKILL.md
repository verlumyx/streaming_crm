# Next.js Module — Validation

Zod schemas handle input validation. They are the **only** place where incoming data (`FormData` in server actions, `searchParams` in pages) is validated and typed.

## Location

```
src/modules/{module-name}/validation/
├── create-{module-name}.schema.ts          create{Module}Schema + Create{Module}Input
├── update-{module-name}.schema.ts          update{Module}Schema + Update{Module}Input
├── update-status-{module-name}.schema.ts   updateStatus{Module}Schema + UpdateStatus{Module}Input
└── search-{module-name}.schema.ts          search{Module}Schema + Search{Module}Input
```

## Rules

1. Always build schemas with `z.object()` from `zod`; export the schema and its inferred type (`type Create{Module}Input = z.infer<typeof create{Module}Schema>`).
2. Schemas contain **no authorization**. The permission check is the first statement of the action (`requirePermission`) or the page (`guardPage`) — see [Authorization](#authorization).
3. Every field that the action reads must be declared in the schema. Never read `formData.get()` or `searchParams.x` directly in actions or pages — use the parsed result.
4. Every message is in Spanish and passed explicitly; never rely on the default English messages.
5. Use `z.coerce.*` for numbers, booleans and dates: every `FormData` and `searchParams` value arrives as a string.
6. Use `safeParse` in actions (return `fieldErrors`) and `parse` in pages (defaults and `.catch()` make it safe).
7. Schemas are plain modules with no `server-only` import, so client forms can reuse them for inline feedback. They never import `@/db`, services or repositories.

## create{Module}Schema

The `id` field is **always required** in create schemas. The UUID v7 is generated by the client (form) and sent with the submission — never generated on the server.

```ts
// src/modules/client/validation/create-client.schema.ts
import { z } from 'zod';

export const createClientSchema = z.object({
  id: z.string({ message: 'El identificador es obligatorio.' }).uuid({ message: 'El identificador no es válido.' }),
  name: z
    .string({ message: 'El nombre es obligatorio.' })
    .trim()
    .min(1, 'El nombre es obligatorio.')
    .max(255, 'El nombre no puede superar los 255 caracteres.'),
});

export type CreateClientInput = z.infer<typeof createClientSchema>;
```

`status` is **not** part of the create schema: new rows are always created as `active` by the repository.

## update{Module}Schema

Same shape as create without `id` (it is a bound argument of the action, validated separately with `z.string().uuid()`).

```ts
// src/modules/client/validation/update-client.schema.ts
import { z } from 'zod';

export const updateClientSchema = z.object({
  name: z
    .string({ message: 'El nombre es obligatorio.' })
    .trim()
    .min(1, 'El nombre es obligatorio.')
    .max(255, 'El nombre no puede superar los 255 caracteres.'),
});

export type UpdateClientInput = z.infer<typeof updateClientSchema>;
```

## search{Module}Schema

Parses the `searchParams` of the Listar page. It must tolerate absent keys (every key is optional or has a default) and must not crash the page on a hand-edited URL, so invalid values fall back with `.catch()`.

```ts
// src/modules/client/validation/search-client.schema.ts
import { z } from 'zod';

export const searchClientSchema = z.object({
  search: z.string().trim().optional(),
  status: z.enum(['active', 'inactive']).optional().catch(undefined),
  limit: z.coerce.number().int().min(1).max(100).default(20).catch(20),
  offset: z.coerce.number().int().min(0).default(0).catch(0),
});

export type SearchClientInput = z.infer<typeof searchClientSchema>;
```

- `limit` defaults to 20 and is capped at 100; `offset` defaults to 0.
- The keys `search` and `status` are the ones the page copies into `SearchClientCommand.filters`; they must match the repository filter map (see `nextjs-module-commands`).
- An empty `search` stays `''` and is skipped by `applyFilters()`.

## Authorization

Schemas validate **shape only**. Authorization is permission-string based: a role (resolved per company) holds action strings of the form `{module}.{action}`, checked by `hasPermission()` from `@/modules/shared/auth/require-permission`. A role with `permissionType === 'all'` (e.g. `Administrador`) passes every check.

Each server action enforces its own permission as its **first statement**, before parsing the input:

| Schema | Action | Permission action |
|---|---|---|
| `create{Module}Schema` | `create{Module}Action` | `{module}.create` |
| `update{Module}Schema` | `update{Module}Action` | `{module}.update` |
| `updateStatus{Module}Schema` | `update{Module}StatusAction` | `{module}.update-status` |
| `search{Module}Schema` | Listar `page.tsx` | `{module}.list` |

```ts
await requirePermission(companyId, 'clients.create'); // throws ForbiddenError → toActionError()
const parsed = createClientSchema.safeParse(Object.fromEntries(formData));
```

- `{module}` is the plural, lowercase slug used in URLs (`users`, `roles`, `clients`) — the same prefix used by the matching page guards and the sidebar menu.
- `requirePermission` denies an unauthenticated session (`getSessionUser()` returns `null`) — it never crashes.
- A `ForbiddenError` is turned into the fixed message `'No tienes permiso para realizar esta acción.'` by `toActionError()` and shown as a toast, so **do not** add custom messaging in the action.
- The GET pages for the same use cases are guarded with `guardPage` (see `nextjs-module-pages`); keep both sides in sync. Full action templates live in `nextjs-module-actions`.

## Using the Schemas

### In server actions — `safeParse` + `fieldErrors`

```ts
const parsed = createClientSchema.safeParse(Object.fromEntries(formData));
if (!parsed.success) {
  return { status: 'error', fieldErrors: parsed.error.flatten().fieldErrors };
}
const command = CreateClientCommand.fromInput(parsed.data, companyId);
```

`fieldErrors` is `Record<string, string[] | undefined>`; the form renders `fieldErrors.name?.[0]` under the field. Only `parsed.data` reaches the Command — never the raw `FormData`.

### In pages — `parse` on `searchParams`

```ts
const filters = searchClientSchema.parse(await searchParams);
```

`searchParams` is a Promise in the App Router — always `await` it first. `parse` is safe here because every field has a default or `.catch()`.

### `FormData` arrives as strings — coerce

```ts
quantity: z.coerce.number({ message: 'La cantidad es obligatoria.' }).int().min(1, 'La cantidad mínima es 1.'),
startsAt: z.coerce.date({ message: 'La fecha no es válida.' }),
notes: z.string().trim().max(500, 'Las notas no pueden superar los 500 caracteres.').optional(),
// checkboxes: an unchecked box is absent, a checked one sends "on" — never z.coerce.boolean() ("false" → true)
isPrimary: z.enum(['on']).optional().transform((v) => v === 'on'),
```

An optional `<input>` left empty sends `''`, not `undefined`. Use `.optional()` with `.transform((v) => v || undefined)` when the column is nullable and an empty string must become `null` downstream.

## Cross-field and async business rules do NOT go here

A schema answers "is this input well-formed?", nothing else. Rules that need the database or the current state of the entity belong in the **Service**, which throws a module exception (see `nextjs-module-exceptions` and `nextjs-module-services`):

- Uniqueness (`ClientAlreadyExistsException`: "Ya existe un cliente con ese correo.").
- Availability / capacity (a profile already sold, a plan without free slots).
- State transitions (`ClientInactiveException`: an inactive client cannot receive a sale).
- Anything comparing the input against another row or against dates computed on the server.

Pure cross-field rules that only look at the submitted values (e.g. `endsAt` after `startsAt`) may use `.refine()` / `.superRefine()` with a Spanish message and a `path`, because they still describe the input, not the domain:

```ts
.superRefine((data, ctx) => {
  if (data.endsAt <= data.startsAt) {
    ctx.addIssue({ code: 'custom', path: ['endsAt'], message: 'La fecha de fin debe ser posterior a la de inicio.' });
  }
});
```

If a rule needs `await`, it is not a validation rule — move it to the Service.
